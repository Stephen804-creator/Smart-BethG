## What Stage 3 means

Stage 3 is the private file and generated-output layer of Smart BethG. It is more than a database table. Users must be able to create, store, list, retrieve, download, verify, and delete their outputs; every record and storage key must be owner-scoped. Social calendars, research reports, code, structured data, and future media-generation results should be stored as artifacts and linked to the mission/project that produced them where applicable.

## Implemented in this branch

- Authenticated artifact API for creating text outputs, listing a user's artifacts, reading text content, downloading outputs, and deleting artifacts.
- Text formats: plain text, Markdown, JSON, Python, JavaScript, HTML, CSV, and YAML. JSON is validated before storage.
- Binary artifact storage for common image, audio, video, PDF, ZIP, and generic binary outputs.
- SHA-256 recorded at creation and verified when content is read/downloaded.
- Versioned PostgreSQL migration 0004 and SQLite additive schema updates for artifact provenance: source type/ID, provider/model, bounded JSON metadata, and an owner/source index. Social calendar exports identify the campaign and export schema; internal generation pipelines can attach provider/model provenance.
- Owner-scoped database queries and owner-prefixed storage keys; local storage rejects traversal and symlinked owner directories.
- Local development adapter and S3-compatible adapter, including AWS S3, DigitalOcean Spaces, MinIO, and compatible object storage.
- Bounded upload reads, 1 MiB text-output limit, and 25 MiB binary-artifact limit.
- A dedicated Artifact Library page plus home-dashboard quick forms for creating text outputs, uploading binary files, listing private artifacts, previewing safe text, downloading, and deleting.
- Social campaign calendar export to a versioned JSON artifact.
- A dry-run-first local-to-object-storage migration utility with checksum/read-after-write verification and explicit retention of source files by default.

## Security and data-handling requirements

- Artifact metadata and file bytes are private; never expose raw storage paths or public bucket URLs in normal API responses.
- Every API read/delete must verify the authenticated owner. Do not treat an unguessable numeric ID as authorization.
- Downloads are forced to attachment, use `nosniff`, and disable shared caching.
- Never execute uploaded/generated code automatically just because it is stored as an artifact. Execution is a separate, policy-controlled capability.
- Store object keys, not cloud access keys, in PostgreSQL. Supply storage credentials through environment/instance identity or a secret manager.
- Take and restore-test database and object backups before production migration. A change from local storage to S3-compatible storage does not migrate files by itself.

## Known limits — do not mark Stage 3 production-complete yet

1. **25 MiB binary cap:** current binary upload/create path buffers a bounded payload in application memory. Large video, audio, and other media require streaming/multipart object upload and provider-specific size limits before the cap is raised.
2. **Object storage scope:** the S3-compatible adapter currently covers artifacts. User uploads and tool workspaces still have separate local-filesystem paths; this is not yet a complete shared-file-storage solution for multiple application replicas.
3. **AI output pipeline integration:** the service can accept generated bytes, but each image/audio/video provider pipeline must explicitly persist its output through the artifact service and attach the artifact to its job/mission. Do not assume every provider output is automatically saved yet.
4. **Quota and lifecycle:** per-user storage quotas, orphan-object reconciliation, retention policies, full account export/deletion, and backup-retention behavior need implementation and end-to-end tests.
5. **Malware/content scanning:** no general file-scanning service is currently wired into this artifact upload path. Treat uploads as untrusted; do not execute or render them inline.
6. **PostgreSQL verification:** the artifact repository/service must be included in PostgreSQL integration coverage, including migration and concurrent operations.
7. **Browser verification:** test the artifact library with two users, CSRF enforcement, failed uploads, binary downloads, missing/corrupt objects, deletion failures, keyboard navigation, and screen readers.
